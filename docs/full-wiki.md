## 来源与版本

- `wiki_original`：Wiki收录的原文，不能冒称全部已独立官网核对。
- `wiki_reference`：Wiki结构化字段；原始属性与显示单位保留区分。
- `site_interpretation`：Wiki解释，可用于事实问答或建议，但需保持归属。
- `site_model`：工具固定条件模型数据，不能作为实战胜率/强度保证。
- `pending`：站点明确标注待确认，普通检索排除；特定待确认问题直接说明边界。
- `official_original`：保留仍能严格匹配旧独立核验文本的字段及官网链接。

历史和下架资料完整归档，默认不作为当前知识检索；显式历史/更新问题可检索。公告只保留各自日期，不自动把多个版本混成“当前规则”。不同模式分开过滤；“通用”表示站点说明或跨玩法公告，不代表跨玩法卡牌数值通用。模型仍可能误读版本，尚无完整的版本生效区间推导。

## 新检索流程

1. 规则处理能力边界、缺项追问及明显待确认问题；新收录实体可用于多轮指代。
2. 对需要检索的真实请求，模型接收问题、近期历史、栏目和实体词表、少量初步匹配标题，返回结构化`queries/keywords/entities/mode/include_history`。参考答案与评测标签不进入请求。
3. 严格校验字段类型、长度、数量和模式。规划超时或非法JSON时，用原问题及基础规则扩展回退；明确标记`fallback`，不会伪装成模型规划成功。
4. 原问题始终保留，与最多4个子查询、关键词共同进行关键词/BM25式排序，先覆盖各子查询再补充结果，最多6条。用户明确指定的模式不能被模型改写。
5. 如问题明确要求某英雄某等级的装备价值，从本地完整分片读取站点结果并附带条件，作为`site_model`证据，而非重新计算实战效果。
6. 模型根据证据回答，后端验证引用ID。响应保留`retrieval_plan`和`query_planning`耗时，前端可展开查看检索词。

Mock模式仍使用规则生成查询，明确标记`mock_rules`。知识问题通常新增一次规划模型调用；闲聊、直接追问和本地拒答不调用规划器。规划预算默认2000 token、20秒，可通过`LLM_PLANNER_MAX_TOKENS/LLM_PLANNER_TIMEOUT_SECONDS`设置，回答预算仍遵守原有配置。没有修改用户`.env`。

关键词生成不能保证永远正确。原词保留和回退只能减少错误传播；无需把改写后的关键词当作事实，也不能把10个检索案例全过当作回答质量验收。

## 重建和更新

离线重建（不需要Node、不联网、不依赖artifacts缓存）：

```powershell
.\.venv\Scripts\python.exe scripts/build_wiki.py --from-snapshot
```

完整刷新（只读公开HTTP，静态解析JS，不执行下载的站点脚本）：

```powershell
npm install --prefix artifacts/wiki-tools --no-audit --no-fund acorn@8.15.0
.\.venv\Scripts\python.exe scripts/sync_wiki.py --tools
.\.venv\Scripts\python.exe scripts/build_wiki.py
.\.venv\Scripts\python.exe -m pytest -q
```

`--reuse-cache`仅供恢复中断采集，不等价于重新联网刷新。网站目录和内嵌数据结构变化可能要求更新解析器；刷新后必须检查覆盖清单和差异，不能只看命令退出码。原始站点模块在忽略的artifacts目录，结构化内容全快照在`data/wiki/snapshot.json.gz`。装备分片独立压缩保存并校验哈希。更新后需重启后端重新加载索引。
